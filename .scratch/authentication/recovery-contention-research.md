# Password recovery: contention and account enumeration

## Answer

Generic responses, timing mitigation, and identifier-scoped concurrency are better supported as a production design than a global PostgreSQL `EXCLUSIVE` table lock. OWASP explicitly recommends generic responses, comparable timing and per-account abuse controls; PostgreSQL documents row-level coordination. Amazon Cognito documents a deployed generic-response mechanism. None of these sources measures prevalence of database locking strategies or discloses Cognito's internal locking. Thus “more common” is an informed inference, not a quantified industry finding; “more stable” is a concurrency/availability inference, not a benchmark.

## Primary-source evidence

- [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#forgot-password-request): return consistent messages for existent and nonexistent accounts, keep response times consistent, consider asynchronous work or comparable logic, and limit automated requests per account. Reset tokens should be securely generated, securely stored, single-use and expiring. OWASP does not prescribe a global lock or guarantee indistinguishable timing under database contention.
- [PostgreSQL explicit locking, table and row locks](https://www.postgresql.org/docs/current/explicit-locking.html): `EXCLUSIVE` table locks conflict with `ROW EXCLUSIVE`, the mode acquired by inserts, updates and deletes, and with other `EXCLUSIVE` locks. Ordinary reads can still proceed: `EXCLUSIVE` is not `ACCESS EXCLUSIVE`. Locks normally last until transaction end. Row locks instead block conflicting writers and lockers of the *same row*, not ordinary queries. Deadlocks can still occur and PostgreSQL aborts a participant. Consequently a table-wide lock serializes otherwise unrelated writes and can amplify stalls or denial of service; row-level coordination limits the affected scope but does not eliminate contention.
- [Amazon Cognito user existence error responses](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pool-managing-errors.html#cognito-user-pool-managing-errors-password-reset): with `PreventUserExistenceErrors` enabled, `ForgotPassword` simulates delivery details for nonexistent, deactivated, or recovery-ineligible users. Console-created app clients default to enabled; API-created clients default to `LEGACY` unless configured. This is an example of response masking, not evidence of any particular database concurrency scheme or perfect timing protection; other flows and configurations have documented caveats.
- [NIST SP 800-63B-4, account recovery](https://pages.nist.gov/800-63-4/sp800-63b.html#issuedrecovery): issued recovery codes must be random, expire, and be throttled on verification; email-issued codes have a maximum 24-hour validity. These are recovery safeguards, not a prescription for table locks, enumeration handling, or proof this local design meets NIST requirements.

## Recommendation for this local project

- Preserve the existing spec: generic acknowledgments/statuses and materially similar timing where practical for known and unknown normalized identifiers; identical per-identifier request limits; one-hour, single-use, superseding reset links; fail-closed completion and session revocation. See [local spec](spec.md). Do not use global `EXCLUSIVE` locking merely to conceal account existence.
- Coordinate conflicting changes for the same account with short transactions and an appropriate account-scoped lock or equivalent atomic constraint; preserve atomic supersession and completion. Different accounts should not wait on one another by design. Avoid holding database locks across mail delivery. Exact mechanism and provider compatibility require validation, not assumptions.
- Row locks alone do not mask contention: an unknown identifier has no account row to lock, while a known identifier may wait behind an in-flight request. Generic bodies alone also do not hide status, latency, timeout, queue, or rate-limit differences. Apply comparable handling to both paths, consider bounded/asynchronous work, handle contention/deadlocks and failures safely, and test externally observable status and latency distributions under deliberately held same-account and unrelated-account locks. Padding cannot guarantee constant time under arbitrary load; test rather than claim it.
- Local scope matters: app is loopback-only; shared inbox, machine and database access are outside isolation boundary, and inbox access reveals activity and permits recovery. Generic responses reduce casual app-level enumeration, not those exposures. Per-identifier limits can be evaded by rotating identifiers; global serialization would worsen availability even for unrelated local users.

## Uncertainties

Sources do not establish prevalence, a universal timing threshold, provider internals, or whether Better Auth and its adapter can enforce the project's exact supersession, delivery-failure and atomic reset requirements. Async delivery changes ordering and failure handling; do not silently weaken those requirements. Validate actual implementation, database contention, and delivery failure behavior before selecting a concrete mechanism. Research accessed 2026-11-02.
