# Research: local email/password authentication planning

## Summary

Next.js provides integration and security guidance, not a complete password-auth product. Better Auth, Auth.js Credentials, Supabase Auth, and a custom implementation place different amounts of verification, reset, session, data-ownership and operational work on the application; none is selected here. Local SMTP capture can exercise email flows without delivering real mail.

## Findings

1. **Framework boundary.** Next.js recommends an authentication library, distinguishes authentication, sessions and authorization, and recommends secure cookie attributes and authorization checks close to data. Proxy alone is not a complete authorization boundary. Next.js 16 renamed Middleware to Proxy; confirm installed-version integration and runtime behavior rather than copying older middleware recipes. **Sources:** [Next.js authentication guide](https://nextjs.org/docs/app/guides/authentication), [Proxy reference](https://nextjs.org/docs/app/api-reference/file-conventions/proxy). **Support:** direct evidence. **Confidence:** high.

2. **Better Auth: integrated application library.** Built-in email/password, verification and reset exist; application supplies verification and reset email callbacks, enables verification requirement explicitly, and connects Next.js route handlers and Drizzle adapter (`pg` supported). It documents scrypt password hashing and session management. Reset does not revoke other sessions by default; opt in with `revokeSessionsOnPasswordReset`. Default signup can reveal existing email; documented protection depends on verification or disabling auto sign-in. Schema migration, email transport, deployment secrets and security configuration remain application responsibilities. **Sources:** [email/password](https://better-auth.com/docs/authentication/email-password), [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle), [Next.js integration](https://better-auth.com/docs/integrations/next), [sessions](https://better-auth.com/docs/concepts/session-management). **Support:** direct evidence; responsibility assessment is interpretation. **Confidence:** high.

3. **Auth.js Credentials: flexible integration, more custom password lifecycle.** Credentials forwards authentication to application logic; official guide explicitly requires implementing password management, including reset, and illustrates custom password hashing. Its Drizzle adapter supports PostgreSQL, but the Credentials provider reference states credentials-authenticated users are not persisted by the provider and require JWT sessions. Do not assume configuring an adapter provides database sessions for Credentials or implements verification/reset. **Sources:** [Credentials guide](https://authjs.dev/getting-started/authentication/credentials), [Credentials reference](https://authjs.dev/reference/core/providers/credentials), [Drizzle adapter](https://authjs.dev/getting-started/adapters/drizzle?framework=next-js), [session strategies](https://authjs.dev/concepts/session-strategies). **Support:** direct evidence and interpretation. **Confidence:** high for documented constraint; validate behavior against pinned release.

4. **Supabase Auth: separate auth service over PostgreSQL.** First-party Next.js and password guides cover email/password, confirmation and recovery; service owns its auth schema and APIs. Application may use Drizzle for its own PostgreSQL tables, but that is not evidence that Drizzle manages Supabase Auth's credentials or sessions. Hosted service adds external dependency; self-hosting adds service operations. Custom SMTP is needed for production delivery; default SMTP has restrictions. **Sources:** [Next.js quickstart](https://supabase.com/docs/guides/auth/quickstarts/nextjs), [password auth](https://supabase.com/docs/guides/auth/passwords), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [self-hosted auth](https://supabase.com/docs/guides/self-hosting/auth/config). **Support:** direct evidence; Drizzle boundary and operational trade-off are researcher inference. **Confidence:** medium; exact Next.js 16 and existing Drizzle integration not verified.

5. **Custom implementation: maximum control, maximum security ownership.** Next.js describes custom session patterns, but application must design password storage, token generation and expiry, verification, reset, anti-enumeration, throttling, session revocation and authorization itself. OWASP recommends slow salted password hashing such as Argon2id and its reset guidance calls for consistent responses and cryptographically random, expiring, single-use tokens. NIST SP 800-63B-4 calls for screening passwords against common or compromised values and rate limiting; its normative requirements apply within its stated scope, not automatically to every app. **Sources:** [Next.js guide](https://nextjs.org/docs/app/guides/authentication), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP forgot password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html). **Support:** direct evidence plus researcher inference on ownership. **Confidence:** high for OWASP password storage; medium for reset and NIST because original pages failed direct fetch and were checked via search snippets only.

6. **Local delivery.** Mailpit provides SMTP capture, a browser inbox and an API for integration testing; point development transport at its SMTP listener and inspect verification/reset links locally. It is a test sink, not production email delivery; protect access because messages contain authentication links. Supabase's local stack may have its own email capture; verify actual project configuration rather than assume ports or integration. **Sources:** [Mailpit project](https://github.com/axllent/mailpit), [Mailpit installation](https://mailpit.axllent.org/docs/install/), [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp). **Support:** direct evidence; security warning and transport integration are researcher inference. **Confidence:** high.

## Contradictions

No direct contradiction found. Auth.js supports database sessions generally, but its Credentials reference explicitly limits that provider to JWT sessions; these statements concern different scopes. Better Auth exposes reset-session revocation but documents it as disabled by default.

## Missing evidence and residual risks

- No repository inspection beyond required skill file: existing schema, dependencies, conventions, branch and git state are unverified. Exact Next.js 16 compatibility and migration behavior must be tested against pinned package versions; documentation alone does not establish it.
- NIST and OWASP reset original-page fetch failed; claims above rely on primary-source search snippets, not full-page inspection. Automated source-check assessment was unavailable; fetched Better Auth and Auth.js passages were manually inspected.
- No hands-on benchmark, end-to-end test, pricing, licensing or maintenance-activity audit performed. Test verification and reset token replay/expiry, enumeration, rate limits, cookie behavior, session revocation, delivery failures and PostgreSQL migrations before adoption.
